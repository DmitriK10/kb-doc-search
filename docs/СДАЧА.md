## 1. Что сделано за 48 часов и что нет

### Работает и показано в видео

**Парсинг DOCX по структуре регламента.** Заголовки (Title / Heading 1-2),
нумерованные пункты, таблицы построчно. Матрица «Роль | Сумма | Подписант»
становится читаемой цитатой, а не картинкой. **SQL-факт корпуса:**
33 активных документа (29 синтетических + 4 реальных регламента),
282 активных чанка (86 синтетических + 196 реальных), 1105 предложений.

**Чанкинг по пунктам, а не фиксированными окнами.** Короткие пункты
склеиваются в пределах раздела, длинные режутся по границам предложений.
Пункты 3.1–3.4 регламента договоров — один чанк 389 символов.

**Гибридный поиск.** PostgreSQL FTS (OR внутри группы синонимов, AND между
группами, потолок 8 групп) + pgvector (halfvec 312, косинус) + слияние
RRF k=60. Проверено на живом PostgreSQL 16 + pgvector 0.8.7: 28/28.

**Sentence-level реранк без вызова модели.** Векторы предложений
предвычислены на индексации; на запросе — одно матричное умножение.
Экономия: −150 мс латентности, −200 МБ RAM.

**Честный отказ.** Калиброванная логистика на 6 признаках + числовой guard.
Признаки (факт из `fusion.py`): `max_sentence_sim`, `top1_chunk_sim`,
`margin`, `rrf_top`, `fts_exact`, `token_coverage`.
Порог подобран на dev-сплите, метрики сняты на test.

**Версионный фильтр актуальности.** EXCLUDE-ограничение в БД: две версии
одного документа не могут действовать одновременно. v2.3 недействительна
с 01.03.2026, поиск её не показывает.

**Аналитика.** Журнал запросов без сырого текста (HMAC), кластеризация
отказов по крону, зоны red/yellow/green, алерты владельцам с дедупликацией.

### Реализовано частично

**Stale-флоу.** Определение «вопрос про недействительную версию» работает,
но в демо-истории таких запросов 1.1%, поэтому сценарий не основной.
Порог `stale_threshold` = 0.62 калиброван отдельно.

**n8n.** Логика алертов живёт в PostgreSQL (`knowledge_alerts`, статус
`pending`), транспорт не подключён. Замена на 40 строк httpx + Telegram Bot
API — следующий шаг. Это осознанно: логика важнее транспорта.

**Разграничение доступа.** Схема и механика готовы (`access_groups`,
кэш с `acl_signature`), значения по умолчанию `{all}`. Реальных групп
в корпусе нет.

### Не сделано

- **LLM-генерация** — сознательно. Галлюцинация исключена архитектурно.
- **PDF-парсинг** — DOCX как обязательный формат для критичных регламентов.
  PDF ломает структуру пунктов.
- **Grafana** — метрики отдаются через `/api/metrics` и видны на стенде;
  отдельный дашборд не развёрнут.
- **Дообучение эмбеддера** — на 75 размеченных вопросах это переобучение,
  а не качество.

## 2. Подход и архитектура

### Путь от запроса до ответа

```
запрос
  ├─ нормализация, токенизация, стоп-фильтр, потолок 8 групп
  ├─ эмбеддинг rubert-tiny2 int8 (2.6 мс)
  ├─ две ветки параллельно, один SQL, фильтр is_active в обеих:
  │    FTS:  OR внутри группы синонимов, AND между группами
  │    VEC:  halfvec(312) <=> , HNSW при >15k чанков
  ├─ RRF k=60 — согласие двух веток побеждает ранг в одной
  ├─ реранк: max-cosine по предвычисленным векторам предложений
  ├─ порядок: косинус + покрытие терминов + совпадение чисел
  ├─ калиброванная логистика (6 признаков) + coverage gate 0.35
  └─ дословная цитата ИЛИ отказ с рекомендацией владельца
```

### Где принимает решения модель

**Только как энкодер.** Модель превращает текст в вектор и не порождает
ни одного слова ответа. Решение «ответить или отказаться» принимает
логистическая регрессия на измеримых признаках.

### Три уровня честности

Продукт даёт не «ответ или отказ», а три исхода.

**Ранний прогон (test, n=38 in-scope)** — цифры до расширения набора:

```
уверенный ответ   16/38   цитата, документ проверен
тир               19/38   похожий фрагмент, проверьте сами
отказ              3/38   ответа нет, маршрут к владельцу
```

**Текущий прогон (test, n=40 in-scope)** — после расширения набора:

```
уверенный ответ   26/40   (A+B = 26+5)
тир                8/40   (C+D = 3+5)
отказ              1/40   (E+F = 0+1)
```

Оба прогона — один продукт, разные размеры набора. Сравнивать доли
нельзя: 16/38 и 26/40 относятся к разным наборам вопросов. В питче
используется **текущий** (26/40), с явным n.

**Ключевая цифра: ни одного отказа при найденном ответе.** Гейт не отрезал
ни одного случая, где нужный пункт был в топ-3. Это самый сильный аргумент
за калибровку.

Тир выдаётся, когда фрагмент найден, но покрытие терминов запроса ниже
порога: цитата может быть не о том. Пользователь видит её с пометкой
и решает сам. Это не компромисс, а честное разделение: отказ заставил бы
искать вручную, хотя нужный пункт, возможно, уже перед ним.

### Известные ограничения (честно)

| Ограничение | Проявление | Статус |
|---|---|---|
| **Опечатка обнуляет покрытие** | «за сколько ПА обязан принять заяву» → отказ, хотя с «заявку» отвечает п. 5.1 | отложено: три подхода к нечёткому сопоставлению дали ложные срабатывания |
| **Ранжирование (Q6)** | «сколько подрядчиков запрашивает TPS» → п. 2.11 на ранк-1, хотя правильный п. 2.12 есть в выдаче (позиция 2). Золото найдено, ранк-1 неверный | отложено: реранк ставит соседний пункт выше по косинусу |
| **Чанкинг пунктов-сборок (Q8)** | «какой срок назначения руководителя проекта» → п. 10.3 (Архитектор) вместо 9.1 (РП) | отложено: чанк 9.1 весит 1129 символов, ответ не доходит до топ-3 |
| **`отказов при найденном gold = 0`** | измерено на n=59 dev / n=40 test | **не гарантия**: набор мал, устойчивость нуля не доказана |

**Про опечатки — замер, а не догадка.** SQL-факт из базы:

```
word_similarity('заяву','заявку') = 0.667   ← опечатка
word_similarity('заяву','визу')   = 0.000   ← чужое слово
word_similarity('срок','строк')   = 0.400   ← ложное срабатывание
similarity('заяву','заявку')      = 0.444   ← обычная similarity не годится
```

Коридор по словам чистый (опечатки ≥0.667, чужие ≤0.500), но на **реальном
корпусе** порог не разделил случаи: три реализации дали либо ложные
срабатывания («визу» отвечал пунктом про заявку), либо ломали верный
ответ («заяву» возвращал п. 1.3 вместо 5.1). Откатили к точному
совпадению. Фикс — в окно доработки, после замера на полном dev-наборе.

### Как выбраны пороги

Свип на dev, gate и tier-min **вместе**, с учётом тира:

| gate | tier-min | dev Recall | dev OOS-safe | test Recall | test OOS-safe | уверенных (dev) |
|---|---|---|---|---|---|---|
| 0.30 | 0.45 | 0.678 | 0.400 | 0.750 | 0.524 | 39 |
| **0.35** | **0.45** | **0.678** | **0.900** | **0.725** | **0.905** | **39** |
| 0.45 | 0.45 | 0.678 | 0.933 | 0.725 | 0.905 | 37 |
| 0.55 | 0.45 | 0.678 | 0.967 | 0.725 | 1.000 | 30 |

**OOS-safe rate** = (H+I)/OOS = 1 − G/OOS: доля исходов на out-of-scope
без ложного уверенного ответа. Не путать с refusal precision.

**Рабочая точка: gate 0.35 + tier-min 0.45.** Критерий: максимум Recall
при OOS-safe ≥ 0.90 на обоих сплитах; тай-брейкер — максимум прямых
ответов. Порог 0.55 даёт лучше OOS-safe, но **девять вопросов теряют
уверенность** (39→30), пять из них с верным ответом, при том же Recall.
Поэтому 0.35.

**Все числа — пост-фикс** (прогон после исправления двойного стемминга).

**Почему это важно:** обычный свип без учёта тира показывал Recall 0.508
вместо 0.678. Тир — это ответ с цитатой и пометкой «проверьте источник»,
а не отказ; если считать его отказом, метрика занижается в 1.3 раза.

**Матрица test (n=40 in-scope, n=21 out-of-scope):**

```
уверенный ответ    A=22  B=4   | OOS: G=2
тир                C=5   D=7   |      H=11
отказ              E=0   F=2   |      I=8
```

### Как проверяется ответ

1. **Цитата дословна по построению** — это подстрока текста чанка.
   Не пересказ, не генерация: пользователь видит проверяемый текст.
2. **Числовой guard.** Если в ответе есть число, которого нет в источнике,
   ответ отсекается детерминированно, независимо от косинусной близости.
   Это ловит главный класс ошибок — неверный срок, сумму, процент.
3. **Ссылка соответствует цитате.** Если процитирован пункт 3.2, ссылка
   говорит 3.2, а не 3.1 (чанк может быть склеен из нескольких пунктов).
4. **Версия.** При вопросе про недействительную версию — ответ по
   действующей с явным предупреждением.

### Дорожная карта: обогащающий слой (после защиты)

Заказчик поднял вопрос: регламенты могут отставать от внешней реальности
(законы, ставки, практика). Сейчас агент работает **только по регламентам**
и честно отказывает, если ответа нет. Что можно добавить — три варианта,
все **после** защиты проекта:

| Вариант | Как | Компромисс |
|---|---|---|
| **1. Зеркало доверенных источников** | ГК, ТК, официальные базы — копия внутри контура, обновление по расписанию | ноль исходящего трафика; нужен регламент обновления |
| **2. Исходящий прокси с санитизацией** | запрос очищается от внутренних данных, allowlist доменов, HMAC-кэш | есть исходящий трафик; нужна экспертиза ИБ |
| **3. Гибрид** | зеркало для частого, прокси для редкого | сложнее в поддержке |

**Ключевое правило для всех вариантов:** внешние сведения всегда идут
с пометкой **«не из регламента»**. Пользователь видит, что это дополнение,
а не цитата документа. Архитектурная гарантия «ответ = подстрока
регламента» сохраняется для основного пути.

**Почему не сейчас:** бриф ограничивает прототип регламентами
(«интеграции в рамках хакатона не нужны»), а обогащение потребовало бы
согласования ИБ и выхода из контура.

### Что подтверждено организаторами

| Вопрос | Ответ | Следствие для нас |
|---|---|---|
| Авторизация на стенде | **допускается** без неё (20:10) | стенд открыт, оценка анонимна |
| Локальный SMTP (mailpit) | **разрешён** (20:13) | сцена письма в кадре легитимна |
| Где живут регламенты | Atlassian Confluence без аддонов (19:36) | пайплайн принимает выгрузки из Confluence |
| Глоссарий | опубликован официально (14:18) | наш SQL-словарь сверяется 1:1, в корпус не кладётся |
| Мощности | 128 ГБ VRAM доступны (17:26) | мы не тратим GPU: CPU-only |
| Методика экономики | токены × ценник + аренда (17:18) | расчёт в поле 4 по этой формуле |

**Про Confluence.** Интеграция не требуется по брифу («интеграции
в рамках хакатона не нужны»). Но пайплайн не привязан к формату
источника: `docx_parser.py` читает DOCX, а выгрузка из Confluence — это
тот же DOCX или HTML, приводимый к тому же потоку блоков. Ответ на Q&A:
«пайплайн принимает выгрузки из Confluence».

### Опора на слова заказчика и организаторов

Три цитаты с **точной атрибуцией** — кто именно это сказал:

| Кто | Когда | Дословно | Что подтверждает |
|---|---|---|---|
| Julia Cherdakova, **заказчик** | 14:51 | «У нас да, есть локальная ллм» | Локальная LLM у заказчика уже есть — она не решила задачу |
| **Организаторы** (чат задачи ИИКузница) | 15:27 | «...не даёт тех результатов, которые мы хотели... хочется увидеть решение, которое двигается по иному пути» | Запрос на **иной путь**, а не на ещё одну генеративную модель |
| **Организаторы** (чат задачи) | 20:10 | «приоритет у качества, регламент может быть в актуализации и пока не обновлен в вики» | Регламент может отставать от факта; расхождение фиксируется запросом в СК для актуализации регламента |

**Важно про атрибуцию:** фраза «двигается по иному пути» — это
формулировка организаторов из чата задачи, а не слова заказчика.
Заказчик подтвердил только наличие локальной LLM. Мы цитируем
источники раздельно, чтобы не приписывать заказчику чужие слова.

**Обоснование кейса 3** — цитата 20:10: если регламент «может быть
в актуализации и пока не обновлен в вики», то ответ владельца должен
попасть в базу раньше, чем обновится документ.

**Важно про иерархию:** агент **не выбирает между регламентами сам**
и **не считает ответ службы качества отменяющим регламент**. При
расхождении агент подсвечивает конфликт и создаёт запрос в СК, который
**фиксирует противоречие для актуализации регламента**. Первоисточник —
регламент; запрос в СК — механизм его обновления, а не подмены.

Это же обосновывает опцию «запрос на сверку регламентов» в развилке
сроков: система не решает, какой срок верный, — она показывает оба
и передаёт расхождение владельцу.

### Дефиниция недостоверности — словами организаторов

> «Недостоверным ответом является ответ, не соответствующий в точности
> информации, которая содержится в регламентах, или дополненный из знаний,
> не содержащихся в регламенте.»

Наша архитектура закрывает это **по построению**: цитата — подстрока
текста чанка, а не пересказ. Дополнить ответ знанием извне физически
нечем: генеративной модели в контуре нет.

### Проверяемость — отличие от решений с дообучением

Наш ответ проверяется **любой** формулировкой: цитата либо есть в
документе, либо её нет. Проверяемость решений с дообучением участник
Тимур (14:53–14:54) поставил под сомнение; организаторы на это
не отвечали, и мы не приписываем им этот вывод.

### Источники данных

30 синтетических DOCX, воспроизводящих структуру реальных регламентов:
договоры (2 версии), командировки, закупки, NDA, ИБ, отпуска, архив, CRM,
премии, штат, удалёнка, обучение, печати, ИТ-заявки, медосмотр, пожарная
безопасность, делопроизводство, материальная ответственность, комтайна.

3 темы намеренно отсутствуют в базе (доверенности, зарубежные командировки,
ИБ-инциденты) — это воспроизведённый сценарий «20–25% запросов без ответа».

## 3. Стек и модели

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык | Python 3.12 | — |
| API | FastAPI + uvicorn, **1 воркер** | Второй воркер удвоит ONNX-сессию и выбьет в OOM |
| Модель | `cointegrated/rubert-tiny2`, 312 измерений | Компактная, русская, работает на CPU |
| Формат модели | ONNX int8, 29.5 МБ | fp32 = 116 МБ; int8 даёт 4× экономию, сдвиг косинуса 0.009 |
| Рантайм | onnxruntime, 2 потока | torch в прод не едет: −200 МБ RSS |
| БД | PostgreSQL 16.16 + pgvector 0.8.7 | halfvec, HNSW, FTS с русским словарём |
| Поиск | FTS + pgvector + RRF k=60 | Согласие двух веток защищает от шума каждой |
| Реранк | numpy по предвычисленным векторам | Без вызова модели на запросе |
| Хостинг | KVM, 2 vCPU, 2 ГБ RAM, 30 ГБ SSD | — |
| Деплой | systemd + nginx, **без Docker** | Экономия ~150 МБ RAM |
| TLS | Let's Encrypt, автопродление | HTTPS обязателен: антивирусы блокируют HTTP |

**Про метрики на расширенном наборе.** Первый замер (30 вопросов) дал
Recall@3 0.864 при refusal precision 0.750. На расширенном наборе
(166 вопросов: dev 97 = 59/30/8, test 69 = 40/21/8) — Recall@3 0.725
на test, отказов при найденном ответе 0.

**Почему цифры меняются между прогонами.** Набор растёт: сначала 38
in-scope вопросов в test, затем 40. Каждый новый вопрос меняет и
числитель, и знаменатель. Цифры ниже — **одного** прогона на текущем
наборе; с прошлыми прогонами они несравнимы.
Это не ухудшение системы, а честное измерение: первый набор строился из
формулировок, близких к тексту корпуса. Компромисс выбран по требованию
брифа: выдуманный ответ дороже отказа.

**Бюджет памяти (замерено):**


в той структуре, которая запрашивается; при появлении шаблона данные
переносятся в него без изменений.

### Инфраструктура

| Статья | Значение | В месяц |
|---|---|---|
| VPS KVM 2 CPU / 2 ГБ / 30 ГБ | уже оплачен | 0 ₽ (существующий) |
| Домен / TLS | Let's Encrypt | 0 ₽ |
| Внешние API | не используются | 0 ₽ |
| LLM-инференс | не используется | 0 ₽ |
| **Итого инфраструктура** | | **0 ₽** |

Стенд разделяет сервер с другими проектами: PostgreSQL занимает 256 МБ

### Стоимость одного запроса

| Ресурс | Расход | Стоимость |
|---|---|---|
Расчёт по методике организаторов (чат 17:18): стоимость запроса =
токены на запрос × официальный ценник провайдера модели + доля аренды
сервера.

| Ресурс | Расход на запрос | Стоимость |
|---|---|---|
| **Токены генерации** | **0** — генеративной модели в контуре нет | **0 ₽** |
| Токены эмбеддинга вопроса | ~20 токенов (**оценка**, 128 макс., int8) | **0 ₽** |
| Доля аренды сервера | 0.15 с из 2 592 000 с/мес | 0.00002 ₽ (VDS ≈ 345 ₽/мес) |
| **Итого** | | **< 0.0001 ₽** |

**Про токены эмбеддинга — раздельно факт и оценка:**

- **SQL-факт:** медиана длины вопроса 38 символов (длины хранятся
  в `query_logs.query_len`).
- **Оценка:** ≈20 токенов — пересчёт от 38 символов по средней длине
  токена rubert (~2 символа). Тексты запросов не хранятся (152-ФЗ),
  поэтому точный замер возможен только токенизацией набора вопросов,
  не реальных запросов.

**Стоимость = 0 ₽**, потому что эмбеддер локальный: провайдера нет,
счёта нет. Аренда сервера считается соседней строкой (VDS ≈ 345 ₽/мес,
доля 0.15 с = 0.00002 ₽).

**Ключевое отличие от решений с генерацией:** у нас расход токенов
не растёт с длиной ответа. Цитата — подстрока документа, её не нужно
порождать. Поэтому запрос на 10 страниц контекста стоит столько же,
сколько на один абзац.

Для сравнения: запрос к внешнему LLM API стоит 0.5–5 ₽. Разница
в 5000–50 000 раз, потому что генерации нет.

**GPU не используется.** Организаторы подтвердили (17:26), что считают
доступными 128 ГБ VRAM — мы не тратим ни байта: инференс CPU-only.

### Экономия для компании

Расчёт по фактическим данным стенда (342 запроса за 30 дней):

| Параметр | Значение | Источник |
|---|---|---|
| Запросов в месяц | 342 | `query_logs` |
| Deflection (строгий) | **60.2%** | success без тира + stale; по нему Time Saved |
| Deflection (полный) | 86.7% | включая тир 26.5% |
| Ручной поиск (медиана) | 60 мин | консервативная граница брифа 60–90 |
| Время ответа системы | 0.16 с | p50 |
| **Сэкономлено** | **206 ч/мес** | (60 − 0.003) × 206 / 60, только строгий deflection |

При потоке 300 запросов и Deflection 84%: **252 ч/мес**.
При пессимистичном сценарии (100 запросов, Deflection 45%): **45 ч/мес**.

**Как отвечать на питче:** «86.7% — полный deflection, включает тир.
Строгий — 60.2%. Time Saved посчитан по строгому, это консервативно:
тир-ответ — цитата с плашкой, сотрудник может всё равно пойти к владельцу.»

Стоимость владения при этом не меняется: 0 ₽ за запрос, существующий сервер.

### Заготовки ответов на питче

**«Recall 0.725 против прежних 0.864?»
Наборы несравнимы. 0.864 — лёгкий набор (22 вопроса, формулировки близки
к тексту корпуса). 0.725 — усложнённый (40 in-scope вопросов: перефразы,
английские формулировки, междокументные). Сравнивать их в одном ряду
некорректно: это разные наборы и разные знаменатели.

**«14 из 21 out-of-scope получили цитату?»**
Это тир, не уверенный ответ. На out-of-scope уверенных ложных ответов
**ноль** (confident precision 14/16 на in-scope, G=0 на OOS). Тир — цитата
с плашкой «похожий фрагмент, проверьте»; `tier_on_out_of_scope` — отдельная
метрика, она не входит в refusal precision.

**«Почему отказывает там, где ответ есть?»**
Precision-first по брифу: «выдуманный ответ дороже отказа». При этом
**ни одного отказа при найденном ответе** — гейт не отрезал ни одного
случая, где нужный пункт был в топ-3. Все 3 отказа — retrieval miss,
они уже посчитаны в Recall@3.

**«Deflection — как посчитано?»**
Две формулы: строгая 60.2% (success без тира + stale), полная 86.7%
(включая тир). n=342, демо-история помечена `is_simulated`, пайплайн
настоящий. Time Saved — только по строгой.

есть»: вектор — промежуточное представление, а не источник утверждений.
Именно поэтому вопрос проверяемости дообученных решений (поднятый
в чате участником) нас не касается: цитата проверяется по тексту документа.

### Про n8n

n8n распространяется по **Sustainable Use License** — это не открытая
лицензия в смысле OSI, есть ограничения на коммерческое использование
как сервиса. В нашем решении n8n **не используется в текущей поставке**:
логика алертов живёт в PostgreSQL, транспорт не подключён. При
необходимости транспорт заменяется на ~40 строк httpx + Telegram Bot API
без изменения логики.
