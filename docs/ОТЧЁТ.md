### Формула Recall@3 — одна, D_g не нужен

```python
recall_at_3 = (A + C) / n_in
```

**Recall@3 = (A+C)/n — «золото в финальном выводе»:** уверенный ответ
ИЛИ тир (тир показывает варианты, пользователь видит золото среди них).

**D_g = C.** Тиры с золотом — это ровно ячейка C, и она **уже входит**
в формулу. Отдельного слагаемого не нужно: формула из кода корректна и
не требует переопределения. На рабочей точке dev C=8, test C=3.

**Почему это снимает конфликт свип-историй:**
- при gate 0.55 пять верных уверенных уходят в тир → они переезжают
  из A в C, а `(A+C)` **не меняется** — Recall тот же. Это и наблюдалось;
- при ослаблении gate отказ с золотом в топ-3 становится тиром или
  уверенным → переезд E→C или E→A, `(A+C)` растёт. (F не переезжает:
у него золота нет.) Это тоже
  наблюдалось.

Обе истории сходятся под одной формулой. Переопределять Recall не нужно.

### Формула refusal precision — выписана

Аналитик нашёл расхождение: «верные отказы / все отказы» даёт dev
9/(9+6) = 0.600, а опубликовано 9/11 = 0.818 (это ДО-фиксные числа; пост-фикс — 4/7 = 0.571). Объясняю.

**Опубликованная формула:** `I / (G + I)`.

- **I** = отказы на out-of-scope, где ответа в базе нет → **верный отказ**.
  dev: 9.
- **G** = уверенные ответы на out-of-scope, где ответа нет → **ложный
  ответ**. dev: 2.

**Знаменатель — не «все отказы», а «все уверенные решения на OOS»:**
отказ (I) или уверенный ответ (G). Тир (H) исключён: это не решение
«ответить/отказать», а цитата с плашкой.

**Почему не I/(I+F) = 9/15 = 0.600.** F — отказы на in-scope, где
золото НЕ найдено поиском. Это **retrieval miss**, а не ошибка решения
об отказе: система не нашла ответ и честно сказала об этом. Считать
такой отказ «неверным» значит штрафовать систему за провал поиска
дважды — он уже учтён в Recall@3.

**Проверка на test:** I/(G+I) = 8/(2+8) = 0.800 — совпадает с
опубликованным. Формула одна для обоих сплитов, скрытых фильтров нет.

**В XLSX знаменатель пишется явно:** «верные отказы / (верные отказы +
ложные уверенные ответы) на out-of-scope».

**Дефиниция confident precision:** `A/(A+B)` — уверенные ответы с gold
на ранк-1 / все уверенные ответы на in-scope. Формула из
`confusion_matrix.py:183`.

**Оговорка:** A включает кейсы, где золото в выдаче, но процитирован
соседний пункт (класс Q6). То есть «A» — это «золото среди первых трёх»,
а не «процитирован именно золотой пункт». Для строгой точности цитаты
нужен отдельный счётчик; в текущей матрице его нет.

**Пост-фикс:** dev 32/(32+7) = 32/39 = **0.821**; test 26/(26+5) =
26/31 = **0.839**.
**До фикса было:** dev 26/29 = 0.897; test 22/26 = 0.846.

Знаменатели выводятся из матрицы полностью — расхождения нет.

**Оговорка про отказы при найденном gold:** dev 0 из 59, test **1 из 40**.
Это измеренный факт на этих вопросах, **не гарантия** для новых.
Устойчивость требует набора в разы больше. Единственный test-случай —
цена гейта, не ретривера: поиск нашёл золото, гейт отрезал.

**Сравнение с прошлыми прогонами некорректно:** 0.864 и 0.711 получены
на других наборах (22 и 38 вопросов). Текущий — 40 in-scope в test.

## 2. Методика свипа: с учётом тира

Обычный свип занижал Recall в 1.3 раза, считая тир отказом. Правильно —

Пересвип выполнен **после фикса** двойного стемминга. Одна таблица,
прогон авторитетным скриптом (`confusion_matrix.py --gate`), факт из БД:

| gate | dev A/B/C/D/E/F | dev Recall | dev OOS-safe | dev ув. | test A/B/C/D/E/F | test Recall | test OOS-safe | test ув. |
|---|---|---|---|---|---|---|---|---|
| 0.30 | 36/9/4/7/0/3 | 0.678 | **0.400** | 45 | 28/6/2/4/0/0 | **0.750** | **0.524** | 34 |
| **0.35** | **32/7/8/9/0/3** | **0.678** | **0.900** | **39** | **26/5/3/5/1/0** | **0.725** | **0.905** | **31** |
| 0.45 | 30/7/10/9/0/3 | 0.678 | 0.933 | 37 | 22/4/7/6/1/0 | 0.725 | 0.905 | 26 |
| 0.55 | 27/3/13/13/0/3 | 0.678 | 0.967 | 30 | 17/2/12/8/1/0 | 0.725 | 1.000 | 19 |

**Recall почти инвариантна к гейту, но не абсолютно.**

- **Вверх (0.35 → 0.45 → 0.55):** уверенный ответ с золотом переезжает
  из A в C (тир), `(A+C)` не меняется. Recall **строго постоянна**:
  0.678 (dev) и 0.725 (test).
- **Вниз до 0.30:** отказы с золотом (E) переехали бы в C, но их 0 на dev
  и 1 на test. Переезжают F → D, а D не входит в `(A+C)`.
- **Единственное исключение — test при 0.30:** Recall 0.725 → **0.750**
  (+1 вопрос). Ячейки: A 26→28, B 5→6, C 3→2, D 5→4, E 1→0, F 0→0.
  Тот самый E (отказ при золоте) на 0.30 стал уверенным ответом.

**Подача:** «Recall практически инвариантна (0.678/0.725 во всём
диапазоне 0.35–0.55); ослабление до 0.30 добавляет максимум один вопрос
и резко роняет OOS-safe до 0.400/0.524. Точка выбирается по OOS-safe
и числу прямых ответов, а не по Recall».

**Почему Recall почти не зависит от гейта — объяснение через формулу.**
`Recall = (A+C)/n`, и C — это **тир с золотом в топ-3**. Когда гейт
ужесточается, уверенный ответ с золотом переезжает из A в C, но сумма
`(A+C)` не меняется. Поэтому 0.678 держится от 0.35 до 0.60.

**При ослаблении ниже 0.35 Recall РАСТЁТ** (0.750 на test): отказы
с золотом в топ-3 становятся тирами (F→C), сумма увеличивается. Но
OOS-safe падает до 0.524 — система уверенно отвечает на вопросы вне
базы. Критерий держит OOS-safe, а не потолок Recall.

**Вывод: D_g отдельно считать не нужно.** Тиры с золотом — это ровно
ячейка C, и она уже в формуле. Формула из кода корректна.

Рабочая точка **0.35 + 0.45**. Порог 0.80 невыгоден: +0.03 precision
за −0.14 Recall.

### Сверка панели с базой (28.11 00:45)

**SQL-факт, счётчики с дефиницией:**

```
РЕАЛЬНЫЕ (NOT is_simulated AND NOT is_service):
  запросов   230   success 120   refusal 110
  сессий       7   уникальных 73
  👍 36          👎 1

ДЕМО (is_simulated, окно 30 дней):
  запросов   300   success 250   refusal 39   прочих 11   strict 61.0%

КЛАСТЕРЫ (прогон 8, без служебных):
  векторов   138   кластеров 8 → тем 6 после агрегации
```

**Условие `hit` из кода дословно:**
```python
def gold_in_sources(sources, gold_ids):
    if not gold_ids:
        return False
    return bool(gold_ids & {s.chunk_id for s in sources[:3]})
```
То есть «золото среди первых трёх в выдаче».

**Демо-блок пересчитан SQL:** 250 success + 39 refusal + **11 прочих** = 300.
«Прочие» — записи с `response_type` вне success/refusal: устаревшая
версия (stale) и служебные проверки внутри демо-истории.
**Strict deflection 61.0% — формула из кода** (`app/main.py:245`):

```
strict = (success + stale − tier) / total = (250 + 11 − 78) / 300 = 0.610
```

Тир вычитается потому, что цитата с плашкой на вопрос вне базы не
экономит время — сотрудник всё равно идёт к владельцу. Полная
(нестрогая) deflection = (success + stale)/total = 0.870.

Проверка: 250 success + 39 refusal + 11 stale = 300 ✓ — три корзины,
четвёртой нет.
Прежние 282/48 были неверны (282 — число активных чанков, копипаст).

**Дефиниция демо 342 vs 300:** в базе **342** демо-запроса (26.10–24.11),
на панели **300** — потому что окно 30 дней отсекает 42 записи старше.
Оба числа верны при своих дефинициях.

**Найден и исправлен дефект кластеризации:** скрипт
`cluster_whitespots.py` не фильтровал `is_service`, поэтому в окно
30 дней попадало 4774 записи, из них **3977 — мои прогоны**. Кластеры
«белых пятен» строились по тестам, а не по реальным вопросам.
После фикса: **546 → 138 векторов, 12 → 8 кластеров**, темы стали
осмысленными (Отпуска 64, Доверенности 24, Договоры 19, Закупки 15,
Справки 10, Автомобиль 6).

**Сумма: 230 = 157 + 35 + 1 + 1 + 1 + 2 + 33** по семи сессиям.

**Дефиниция «261 ч сэкономлено»:** сумма (60 мин − время ответа) по всем
не-отказам демо-истории, делённая на 60.

**Дефиниция «48% отказов»:** доля `refusal` среди не-служебных запросов (110/230 = 47.8%).
Высокая, потому что тестировщики намеренно задавали вопросы вне
регламентов — проверка честного отказа.

**Метки наборов:** демо (342/300, синтетика) и реальные (230, тесты
команды) — разные наборы, не смешивать.
