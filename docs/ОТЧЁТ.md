Без этой оговорки цифра 0.571 выглядит как регресс, хотя это следствие

OOS-safe (Δ +0.034 против −0.033 на dev).

### Таксономия ячеек матрицы (формулы)

| Ячейка | Дефиниция |
|---|---|
| **A** | уверенный ответ, gold на ранк-1 |
| **B** | уверенный ответ, gold вне топ-3 |
| **C** | уверенный ответ, gold в топ-3, но ранк-1 неверный (класс Q6) |
| **D** | тир: цитата есть, но совпадение слабое — уточняющий вопрос |
| **E** | отказ, хотя gold был в топ-3 (потеря) |
| **F** | отказ, gold вне топ-3 (класс Q8 — не найден поиском) |

**Разложение без остатка:**

```
dev:  A+B+C = 47 (уверенные) + D = 9 (тир) + E+F = 3 (отказы) = 59
test: A+B+C = 34 (уверенные) + D = 5 (тир) + E+F = 1 (отказ)  = 40
```

**Формулы метрик:**

```
Recall@3          = (A+C) / (A+B+C+D+E+F)
confident_precision = A / (A+B)          <- формула в коде
OOS-safe rate     = (H+I) / (G+H+I) = 1 − G/OOS
refusal_precision = I / (G+I)
```

**Почему C входит в Recall:** золото в выдаче — пользователь видит
нужный пункт среди трёх, пусть и не первым. Ранк-1 неверный
учитывается отдельно в confident precision.

**Почему D не входит в confident precision:** тир — это не уверенное
утверждение, а приглашение проверить. Считать его «точным ответом»
значило бы выдавать сомнение за уверенность.

### Confident precision пост-фикс — формула из кода

В коде метрики стоит `A/(A+B)`, не `A/(A+B+C)`:

```
dev:  32/(32+7) = 32/39 = 0.821   (было 0.897 до фикса)
test: 26/(26+5) = 26/31 = 0.839   (было 0.846 до фикса)
```

**Счётчики до/после:**

| | dev до | dev после | test до | test после |
|---|---|---|---|---|
| A (верный ранк-1) | 26 | **32** | 22 | **26** |
| B (gold вне топ-3) | 3 | **7** | 4 | **5** |
| A/(A+B) | 0.897 | **0.821** | 0.846 | **0.839** |

**Честная сделка целиком:** Recall +0.034/+0.050, отказы 20→7 (dev) и
13→3 (test), тиры выросли с 12→17 (dev) и 3→9 (test), точность ранк-1
у уверенных просела 0.897→0.821 (dev) и почти не изменилась на test
(0.846→0.839). OOS-safe 0.900/0.905.

Причина просадки на dev: покрытие считается верно, поэтому больше
вопросов проходит гейт как уверенные — включая те, где совпадение слов
частичное. Отсюда B вырос 3→7.

### Формула refusal precision — выписана

Аналитик нашёл расхождение: «верные отказы / все отказы» даёт dev
9/(9+6) = 0.600, а опубликовано 9/11 = 0.818. Объясняю.

**Опубликованная формула:** `I / (G + I)`.

- **I** = отказы на out-of-scope, где ответа в базе нет → **верный отказ**.
  dev: 9.
- **G** = уверенные ответы на out-of-scope, где ответа нет → **ложный
  ответ**. dev: 2.

**Знаменатель — не «все отказы», а «все уверенные решения на OOS»:**
отказ (I) или уверенный ответ (G). Тир (H) исключён: это не решение
«ответить/отказать», а цитата с плашкой.

**Почему не I/(I+F) = 9/15 = 0.600.** F — отказы на in-scope, где
золото НЕ найдено поиском. Это **retrieval miss**, а не ошибка решения
об отказе: система не нашла ответ и честно сказала об этом. Считать
такой отказ «неверным» значит штрафовать систему за провал поиска
дважды — он уже учтён в Recall@3.

**Проверка на test:** I/(G+I) = 8/(2+8) = 0.800 — совпадает с
опубликованным. Формула одна для обоих сплитов, скрытых фильтров нет.

**В XLSX знаменатель пишется явно:** «верные отказы / (верные отказы +
ложные уверенные ответы) на out-of-scope».

**Дефиниция confident precision:** уверенные ответы, у которых gold
найден / все уверенные ответы на in-scope. dev: 26/(26+3) = 26/29 =
0.897. test: 22/(22+4) = 22/26 = 0.846. Знаменатели выводятся из матрицы
полностью — расхождения нет.

**Оговорка про «0 отказов при найденном gold»:** набор мал (n=59 / n=40).
Ноль — измеренный факт на этих вопросах, **не гарантия** для новых.
Устойчивость требует набора в разы больше.

**Сравнение с прошлыми прогонами некорректно:** 0.864 и 0.711 получены
на других наборах (22 и 38 вопросов). Текущий — 40 in-scope в test.
